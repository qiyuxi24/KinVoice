## 账户系统 & user_id 传递链路规范化（2026-07-05 下午）

### 修复动机
- 上次 P0#2 统一了 chat.py/memory.py 用 X-User-Id Header，但 family.py 和 chatroom.py 仍从 body/query 读 user_id，同一请求两套传递方式冲突
- getUserId() 在 init() 完成前返回 null → ajax.js 注入空 Header → 后端 fallback 到 "1"
- 登录入口分散，需要统一到 Profile 页面点击头像登录

### 改动汇总

| 层 | 文件 | 改动 |
|----|------|------|
| 后端 | `api/family.py` | 所有5个端点改用 `Depends(get_user_id)`；移除 `user_id` from 4个请求模型；删除 `LeaveGroupRequest` |
| 后端 | `api/chatroom.py` | 3个端点改用 `Depends(get_user_id)`；移除 `user_id` from body/query |
| 后端 | `schemas/chatroom.py` | SendMessageRequest 移除 user_id 字段 |
| 前端 | `userIdentity.js` | 模块加载时 eager 生成 UUID（`_cachedUserId = eagerUuid`），确保 getUserId() 永远不返回 null；init() 从 storage 恢复已有 UUID 覆盖缓存 |
| 前端 | `apis/family.js` | 删除 uid() 辅助函数 + `import userIdentity`；5个方法全部移除 user_id 传参 |
| 前端 | `apis/chatroom.js` | 删除 uid() + `import userIdentity`；3个方法全部移除 user_id |
| 前端 | `pages/Profile/index.ux` | **登录入口**：未注册显示"未登录"+ "点击头像登录 / 设置昵称"；头像显示"?"；弹窗标题"设置昵称以登录"、按钮"登录"；已注册显示"点击修改用户名"+"确认"；toast 区分"登录成功！"/"用户名已更新" |

### 数据流（规范化后）
```
前端 ajax.js → 自动注入 X-User-Id Header（从 userIdentity.getUserId()）
后端 get_user_id 中间件 → 从 Header 提取，未传默认 "1"
所有 API（/chat /family /chatroom /memory /profile_ai）统一 Depends(get_user_id)
前端 family.js/chatroom.js 不再往 body/query 传 user_id
```

### 竞态修复原理
```
模块加载 → eagerUuid = generateUUID() → _cachedUserId = eagerUuid
         → getUserId() 随时可用（不返回 null）
app.ux onCreate() → userIdentity.init()
         → initUserId() → storage.get('kinvoice_user_id')
         → 如有旧 UUID → _cachedUserId 被覆盖为旧值
         → 如无 → 持久化 eagerUuid，保持不变
```

## 主动信号机制（2026-07-05 晚间补充）

### 问题
定期后台提取（每3/5轮）无法响应用户的明确请求。用户说「帮我记下来」时，Cloudie 没办法触发保存。

### 方案：Cloudie 回复中插入 HTML 注释标记
- `<!--PROFILE-->`：触发动态档案更新
- `<!--CARD-->`：触发传承卡片提取
- 标记是给后台系统的指令，后端 `_parse_signals()` 正则剥离后用户永远看不到
- 标记只放在回复末尾，两个可同时加，互不冲突

### 完整数据流

```
用户：「我升职了，帮我记下来」
  → Cloudie LLM 回复：「恭喜！太棒了🎉<!--CARD--><!--PROFILE-->」
  → chat.py _parse_signals() → clean_reply="恭喜！太棒了🎉" + has_card=True + has_profile=True
  → 保存 clean_reply 到 DB
  → asyncio.create_task(_handle_signals):
      ├─ update_dynamic_profile(user_id, messages)   ← 独立 Profile AI prompt
      └─ summarize_to_notes(messages) → Card 表       ← 独立 Cards AI prompt
  → asyncio.create_task(_background_extract)          ← 定期提取（不变）
  → 返回 clean_reply 给前端（用户看不到标记）
```

### 改动文件

| 文件 | 改动 |
|------|------|
| `cloudie_prompt.py` | 新增「主动记录」章节：告知 Cloudie 何时加标记、标记格式、位置规则、示例对话 |
| `chat.py` | 新增 `_parse_signals()` + `_handle_signals()`；chat endpoint 中在 `call_llm` 之后、保存 DB 之前调用 `_parse_signals` 剥离标记；保存清洁文本到 DB；`asyncio.create_task(_handle_signals)` 处理信号 |

## userIdentity 模块加载时 init() 导致 storage 时序崩溃（2026-07-05 深夜）

### 报错
```
app.js:26 Uncaught TypeError: _userIdentity.default.init is not a function
    at XApp.onCreate (app.js:26)
web.js:1 Uncaught (in promise) Error: 请确认Native方法调用[system.storage.get()]
    发生在应用app的生命周期的创建['onCreate()']之后
```

### 根因
`userIdentity.js` 第 177 行在**模块加载时**（import 阶段）就调用了 `userIdentity.init()`，此时 app 生命周期尚未开始，`storage.get()` 抛出异常。这导致：
1. 模块导出被破坏 → `app.ux` 的 `import userIdentity` 得到异常值 → `userIdentity.init()` 报 `is not a function`
2. Native 拒绝 storage 调用 → "请在 onCreate() 之后调用"

### 修复

| 位置 | 改动 |
|------|------|
| `userIdentity.js:177` | **删除**模块级 `userIdentity.init()` 自动调用 |
| `userIdentity.js:51-52` | 新增 `_userIdPromise` / `_nicknamePromise` 缓存守卫 |
| `userIdentity.js:94-95` | `initUserId()` 加 `if (this._userIdPromise) return this._userIdPromise` |
| `userIdentity.js:122` | `initUserId()` 末尾 `return this._userIdPromise` |
| `userIdentity.js:131-132` | `initNickname()` 加 `if (this._nicknamePromise) return this._nicknamePromise` |
| `userIdentity.js:145` | `initNickname()` 末尾 `return this._nicknamePromise` |

### 修复后的初始化时序
```
app.ux onCreate() → userIdentity.init() [同步设置守卫 Promise]
  → initUserId() 开始（async storage.get）
  → initNickname() 排队

[页面创建]

ProfileTab/其他组件 onInit → await userIdentity.initUserId()
  → 命中 _userIdPromise 缓存 → 直接返回同一个 Promise（不会重复调 storage）
  → await userIdentity.initNickname()
  → 命中 _nicknamePromise 缓存 → 同上
```

### 为什么模块加载时不能调 storage
快应用的 `@system.storage` 是 Native API，必须在 `app.onCreate` 之后才能使用。模块加载（import/require 阶段）早于任何生命周期，此时调用必然失败。

`ajax.js` `fetchPromise()` 把所有 fetch 调用包在 `userIdentity.ready().then(() => {...})` 里：
- 如果 `ready()` 因为任何原因没有 resolve → **所有 API 请求永久挂起**
- MemoryTab `async loadAll()` 第一行 `await $apis.cards.listFolders()` 卡死 → `loading=true` 永远不释放
- CompanionTab `syncFromBackend()` / `fetchFamilyId()` 也卡死
- 虽然 `Promise.race` 有 20 秒超时，但超时后悔 catch 吞掉 → 用户看到空白/转圈

### 修复
将 `ajax.js` `fetchPromise()` 回退为**同步 Header 注入** + fire-and-forget `ready()`：

```js
// 同步注入（getUserId() 始终有值：eagerUuid 或 storage 恢复的 UUID）
const uid = userIdentity.getUserId()
if (uid && !fetchOptions.header['X-User-Id']) {
  fetchOptions.header['X-User-Id'] = uid
}

// fire-and-forget：确保初始化运行但不阻塞请求
userIdentity.ready().catch(() => {})
```

### 设计逻辑
- `getUserId()` 永远返回一个 UUID（模块加载时生成 eagerUuid 作为 fallback）
- 首次启动：eagerUuid 被 `initUserId()` 持久化到 storage → 二者一致
- 重新启动：eagerUuid 是随机值，但 `storage.get()` 通常极快（μs~ms），在首次 API 调用前就已完成
- 如需精确 UUID（如 Family 页面），调用方自己 `await userIdentity.ready()`
- `ajax.js` 作为通用层不应阻塞所有请求

## ProfileDetail 永远显示"加载中..."（2026-07-05 深夜）

### 问题
ProfileDetail 页面始终显示"加载中..."，无法正常使用。

### 根因
`loadProfile()` 方法顶部的守卫存在逻辑错误：

```js
// private: { loading: true }  ← 初始 true

async loadProfile() {
    if (this.loading && this.content === '') return  // 首次调用命中此条件，直接 return
    this.loading = true
    // ... 永远不会执行到这里
}
```

`loading` 初始化为 `true`，`content` 初始化为 `''`，`onInit()` → `loadProfile()` 第一行就命中守卫条件，直接 `return`，请求从未发出，`loading` 永远为 `true`。

### 修复
1. `loading` 初始值改为 `false`
2. 守卫条件简化为 `if (this.loading) return`（移除 `&& this.content === ''` 条件）
3. `onShow()` 已有 `if (!this.loading)` 防护，不会重复触发

## ChatRoom 家庭群聊白板修复（2026-07-05 深夜）

### 问题
ChatRoom 页面（`/pages/ChatRoom`）显示为白板，完全无内容。

### 根因（多个）
1. **`async onInit()` 无 try/catch**：`userIdentity.initUserId()` / `ensureConversation()` / `loadMessages()` 中任一步失败或抛出异常，整个 `onInit` 崩溃，Quick App 可能不渲染模板
2. **缺少错误状态 UI**：模板只有 `loading` 和空消息两种状态，加载失败时无任何提示
3. **模板表达式无防御**：`(msg.sender_nickname || '我').charAt(0).toUpperCase()` 在 Quick App 某些运行时可能因类型问题抛错
4. **数据解析无空值保护**：`res.conversations` 如果返回 undefined 会直接抛 TypeError

### 重构要点

| 改动 | 说明 |
|------|------|
| 生命周期拆分 | `onInit()` 只做同步初始化（设置路由参数、标题），异步流程移至 `_initFlow()` 独立方法 |
| 新增 `loadError` 状态 | 加载失败时显示错误提示 + "点击重试"按钮 |
| 新增 `retryLoad()` | 重试整个初始化流程 |
| `_initFlow()` 全 try/catch | 步骤 1 用户身份 → 步骤 2 查找会话 → 步骤 3 加载消息 → 步骤 4 轮询，每步检查 `checkActive(this)` |
| 模板状态机 | `loading` → 加载中 / `loadError` → 错误+重试 / `messages.length===0` → 空状态 / 否则 → 消息列表 |
| 模板辅助方法 | `showAsSelf(msg)` + `avatarChar(msg)` 替代内联表达式，带 null/undefined 防护 |
| `else/elif` 条件链 | Quick App 中 `if`/`elif`/`else` 互斥渲染比 `if` 平铺更可靠 |
| 底部输入区始终可见 | 加载中/错误时 `disabled`，不隐藏 |
| 移除 `scrollToBottom()` 多余调用 | 减少 100ms→150ms 延迟，防止 DOM 未就绪 |
